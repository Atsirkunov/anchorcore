Trust / Security notes

Security notes: what AnchorCore sends, stores and gates

This is the long version of the trust section on the landing page. Each statement points at the file in the public repository that backs it, so you can check it rather than take our word. Paths are under rust/crates/anchorcore/src/ unless noted. Where something is a limit rather than a protection, it is listed under Known limits.

AnchorCore is a private AI search app: it indexes your files and connected sources on your machine and returns cited answers. It has not been through a SOC 2 or ISO 27001 audit or a third-party penetration test, and it has no SSO or role system. Nothing here is a certification.

Every outbound network call

With no connector and no cloud key configured, the app makes no outbound connections: indexing, keyword search and local answers need no network. The calls it can make are the ones below; every HTTP client in the source is one of these.

Source labels and the cloud gate

Every source carries one label: internal (the default), public, sensitive or pii. A provider counts as approved when it is a local endpoint (http:// to localhost, 127.0.0.1 or ::1), when its URL is listed in ANCHOR_TRUSTED_PROVIDERS, or when ANCHOR_CLOUD_TRUST=1 is set. Localhost is always approved; any cloud endpoint needs one of the other two. Evidence: common.rs (provider_is_local, provider_trusted).

LabelLocal modelApproved cloudUnapproved cloud
internal, publicYesYesYes
sensitive, piiYesYesHeld back
  • Answers. Hits from sensitive or pii sources are removed before passages go to an unapproved cloud answer model, and a system_events warning records how many were excluded. If nothing survives, the app says relevant knowledge exists but cannot be used, instead of guessing. (answer.rs: gate_answer_hits, record_gate_event.)
  • Indexing. Indexing uses no chat model at all. Sensitive and pii sources skip an unapproved cloud embedder, and the background backfill leaves their chunks unembedded. They stay keyword-searchable. (pipeline.rs, scheduler.rs.)
  • Follow-up rewrite. Skipped when the answer provider is not approved. (answer.rs.)
  • Public answers. POST /qa/public answers only from sources labelled public, and the MCP public_only option calls that path. (answer.rs, main.rs, mcp.rs.)

The gate keys on the source label. It is a decision you make when connecting a source, so it is only as good as the label you picked.

PII marks are manual

There is no automatic PII detection. A person can mark a whole document as PII (PATCH /items/:id with is_pii, or the toggle in the Entities view). The mark is visible and survives backup, but it does not gate cloud flows on its own yet: gating is by source label, as above. If a document must never reach an unapproved cloud model, keep it in a source labelled sensitive or pii. (items.rs; the decision is recorded in rust/docs/decisions.md.)

Where credentials are stored

  • Connector credentials (token, API key, password, client secret) are stripped out of a source's config before it is saved, so the database row holds none, and reading the config back returns them masked. The cloud answer and embedder API keys are stored the same way. (secrets.rs, settings.rs.)
  • The store tries the operating system keychain first, which is the credential store of macOS and Windows. If that is unavailable it writes one encrypted file per key in your data folder (secrets.enc.*), with the encryption key in a file beside them (permissions 0600 on Unix). That guards against casual reading of a copied file, not against someone who can read your whole data folder.
  • We have not verified keychain behavior on Linux, so we make no claim about it; expect the encrypted-file fallback there unless you have tested otherwise.
  • The API masks stored secrets as ***set*** when a source's configuration is read back. The log is anchorcore.log in your data folder.

Who can reach the app

  • Personal. The app binds 127.0.0.1 by default and has no sign-in, so anyone using your computer account can open it. Requests are checked against a Host/Origin allowlist (localhost plus ANCHOR_CORS_ORIGINS) and carry a CSRF token. If you start the Personal app with --host 0.0.0.0 yourself, it does not stop you, and there is no password unless you set ANCHOR_AUTH_SECRET. (main.rs, security.rs, auth.rs.)
  • Team (self-hosted). The container listens on 0.0.0.0:8000 behind your own proxy; the app speaks plain HTTP, so terminate TLS in front. With ANCHOR_AUTH_SECRET set, password sign-in is on (PBKDF2 password hashes, HS256 session tokens, five failed attempts lock that key out for 60 seconds). Without it the Team edition refuses to start on a non-loopback address. There are no roles: every signed-in user sees the same index. See For teams and hosting/README.md.
  • The Team license is verified offline at startup; no license server is contacted. (license.rs.)

What is recorded

The app keeps a system_events table in its database. It receives gate refusals, sync errors, retrieval degradations and one entry for every agent ask and search call over MCP (component mcp, with the first 80 characters of the query and the hit count). The table is local and is not sent anywhere. (answer.rs, pipeline.rs, mcp.rs.) It is a log, not a tamper-evident audit trail: anyone with write access to the database can alter it.

Backups

An export is one .anchorcore-backup file. Source credentials are left out unless you opt in with a passphrase, which puts them in a separate encrypted bundle; provider API keys are never exported. Imports can be previewed with a dry run first. The archive itself is not encrypted, so store it as you would the data it contains. Details: docs/backup.md.

Verify your download

Each release carries a SHA256SUMS file next to the downloads (the macOS DMG and the zips, generated in .github/workflows/release.yml). Put it in the same folder as your download, then:

macOS / Linux:  shasum -a 256 -c SHA256SUMS --ignore-missing
Windows:        Get-FileHash .\AnchorCore-windows.zip -Algorithm SHA256
                (compare with the matching line in SHA256SUMS)

The checksum shows the file is the one the release published; it does not prove who built it. If that matters to you, build from source.

Signing status. The macOS app is ad-hoc signed and not notarized by Apple. The Windows and Linux builds are not code-signed. Nothing is signed through an app store. That is why first launch needs "Open Anyway" on macOS or "Run anyway" in Windows SmartScreen. Release notes: docs/release-notes.

Known limits

  • The JSON API connector has no address guard. It sends requests to whatever address you enter, including localhost and private network addresses, and a full URL in list_path is used as-is. There is no SSRF or private-address protection. Enter only addresses you trust, and treat anyone who can edit sources as able to make the app send requests from your machine or server. The Team edition has no roles to restrict who that is.
  • Personal has no sign-in; it relies on being bound to your own machine.
  • The gate works on source labels. Per-document PII marks are advisory today.
  • Once passages go to a cloud model you approved, that provider's own handling applies; AnchorCore cannot see or control it.
  • The index is a SQLite file that AnchorCore does not encrypt at rest. Use full-disk encryption if the device can be lost.
  • No SOC 2, ISO 27001, SSO, role-based access control or third-party penetration test.
