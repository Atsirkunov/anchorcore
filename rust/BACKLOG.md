### Phase 30 — Ingestion throughput + job coordination (owner report 2026-10-12; rescoped 2026-10-26 for model-free ingest) — 3 open / 5 shipped

> Owner report: a 513-file folder took ~1 h to get through 200 files on an M4 Mac (32 GB) and is still slower than expected on a 5090 box. Live diagnosis 2026-10-12 (Windows, 1.0.21, source 3 "My folder"): sync + reclassify were both `running` over the same 513 files (`jobs` 10/11, created 4 s apart — the UI job badge lags the click by one poll, so the second button is still live); sampled live: reclassify 4.0 s/file, sync 15.0 s/file, while Ollama sat at 5% CPU (a full classify call measures ~0.6 s on this box) and the app burned 67% of a core — the wall time is contention + per-file pipeline work, not model speed. Three multipliers, worst first: duplicate jobs on the same data (R30.1), strictly serial documents in the pipeline (R30.2), the watcher fallback re-extracting the whole folder ~once a second (R30.3). Instrumented run 2026-10-12 (per-phase debug logs, scratch DB with 609 tags): a 1 KB code file = ~0.3 s app work + ~0.8 s classify + ~0.4 s embed; the 443 KB PDF item `corpevents-2021-12.en.pdf` = detect 0.5 s, classify **90 s** (54 windows), tags **8.1 s** (2766 `ensure_tag` calls, 657 full-tag-table scans), pii **28 s**, embed 24 s; the 78 KB `integration_test.go` = tags 1.4 s, pii 2.5 s. The 2.7 MB text corpus yields ~660 classify windows, but the 16 KB / 50 %-overlap windowing re-feeds roughly 2.3x the unique text in prefill — the dominant cost on any machine, and why the M4 spends ~15 s/file. Of the two PDFs, `corpevents` (2 MB) is real text (8 % of windows) and `vendor-whitepaper.pdf` (5 MB) extracts to **empty text** yet is re-extracted and re-ingested on every sync (R30.5). Second owner report the same day (live, 2 jobs running): the UI shows a single `Stop` and it does not say which job it kills — see R30.4.
