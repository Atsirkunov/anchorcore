## 3. Findings

### F-01 — High — Team deployment is fully readable/writable by any LAN peer when `ANCHOR_AUTH_SECRET` is unset

- **Where:** [security.rs:108](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/security.rs:108) (`is_host_allowed` trusts the client-supplied `Host` header), [security.rs:137](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/security.rs:137) (missing `Origin` is allowed), [security.rs:251](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/security.rs:251) (`GET /csrf` hands the per-session token to any caller that passes Host/Origin), [auth.rs:99](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/auth.rs:99) (auth off unless the env var is set), [hosting/Dockerfile](/Users/aleksandrtsirkunov/anchorcore/hosting/Dockerfile:1) (`--host 0.0.0.0`), [hosting/.env.example](/Users/aleksandrtsirkunov/anchorcore/hosting/.env.example:1) (`ANCHOR_AUTH_SECRET` shipped commented out).
- **Scenario:** An operator follows the Team quickstart, sets only the license, and publishes `8000:8000` on a LAN/VPC host. A peer on the same network runs `curl -H 'Host: localhost' http://team-host:8000/csrf`, receives the CSRF token, then reads every source, item and entity, browses the container filesystem via `GET /system/fs?path=/`, and exports a full backup with `POST /backup/export`. No browser, no DNS rebinding, no credentials are involved.
- **Why it fails:** Host/Origin checks are a browser DNS-rebinding defence; they authenticate nothing, because a non-browser client chooses both headers. CSRF only proves the caller fetched `/csrf`, which is public by design. The only real gate is `ANCHOR_AUTH_SECRET`, and the shipped example leaves it off while the container binds all interfaces. The hosting README does say "keep the port private then", but the default artefact (published port, auth commented out) fails open.
- **Status:** Confirmed by code trace. Personal mode is unaffected (loopback bind, [main.rs:125](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/main.rs:125)).
- **Minimal fix:** In Team edition (`ANCHOR_EDITION=team`), refuse to boot on a non-loopback bind without `ANCHOR_AUTH_SECRET` (or generate a one-time setup credential), mirroring the existing license gate at [main.rs:598](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/main.rs:598).
- **Regression test:** Boot-config unit test: `edition=team + host=0.0.0.0 + no auth secret ⇒ exit/error`; `+ secret ⇒ boots`; personal loopback without secret still boots.

### F-02 — High — Embedding backfill sends label-gated (sensitive/PII) chunks to an untrusted cloud embedder

- **Where:** [scheduler.rs:218](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/scheduler.rs:218) `backfill_batch` selects **all** chunks with `embedding IS NULL` with no source-label join and calls `embedder.embed` directly ([scheduler.rs:235](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/scheduler.rs:235)). The ingest-time gate it bypasses is [embedder.rs:159](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/embedder.rs:159) (`embed_gated` returns all-`None` for gated sources) applied at [pipeline.rs:1460](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:1460). Backfill starts at boot ([main.rs:382](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/main.rs:382)) and repeats every 15 min.
- **Scenario:** A `sensitive`-labelled folder is synced while `embed_base_url` points at a cloud embeddings API without `ANCHOR_CLOUD_TRUST=1`. Ingest correctly leaves those chunks unembedded. Within seconds of the next backfill pass (or the next restart), the raw chunk text is POSTed to that cloud endpoint — exactly the transfer the label exists to prevent. Chunks from manually PII-marked items (`ingested_items.is_pii`) are sent the same way, because the query does not look at items at all.
- **Why it fails:** The backfill's stated premise ("ingest already applied the trust gates", [scheduler.rs:186](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/scheduler.rs:186)) is inverted for gated chunks: they are `NULL` *because* the gate refused, and `NULL` is the backfill's only selection criterion. Gated and merely-failed chunks are indistinguishable in this query. This is a deliberate trade-off in the codebase (the safety net that drains IDF-skipped chunks), but its privacy cost is not contained: it silently defeats the source label, which the UI promises as "never sent to cloud providers" ([SourceForm.tsx:12](/Users/aleksandrtsirkunov/anchorcore/frontend/src/tabs/sources/SourceForm.tsx:12)).
- **Status:** Confirmed by code trace; existing backfill tests ([scheduler.rs:330](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/scheduler.rs:330)) seed only an ordinary source, so the gap is untested.
- **Minimal fix:** Exclude chunks whose owning item's source is `sensitive`/`pii` (or whose item `is_pii=1`) when the embed provider is untrusted — i.e. join `ingested_items`/`sources` in `backfill_batch`, or route the batch through `embed_gated` per source. Keep the ungated behaviour for ordinary sources so `pending_embeddings` still drains.
- **Regression test:** Seed a `sensitive` source with a NULL-embedding chunk, point the embedder at a mock server, run `backfill_once`, assert the mock received no request and the chunk stays `NULL`; assert an ordinary chunk in the same DB still embeds.

### F-03 — High — A cancelled or failed sync leaves the document permanently marked up-to-date

- **Where:** [pipeline.rs:634](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:634) `upsert_doc` commits the new `content_hash`, text and stat fingerprint **before** classification; classification runs afterwards as a sequence of independent DB writes ([pipeline.rs:869](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:869) `finalize`: window hashes → doc chunks → summaries → tags → distill → embed, each its own `run_db` call). The skip decisions that then suppress re-work are the fingerprint check at [pipeline.rs:602](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:602) (folder) and the content-hash check inside `upsert_doc` itself ([pipeline.rs:641](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:641)) plus `sync_fetched_doc` at [pipeline.rs:539](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:539).
- **Scenario:** A user syncs a 200-file folder and cancels the job (or the classifier provider dies) while file #50 is mid-classification. The job is honestly reported `cancelled`, but file #50's hash/fingerprint already match its new content. Every later sync returns `Skipped`/`unchanged` for it: its entities are missing or half-written (windows processed before the cancel check at [pipeline.rs:857](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:857) were stored, later ones were deleted as stale or never created), its doc chunks may be the old version, and nothing ever re-queues it short of a manual force-reclassify. Retrieval then answers from a silently incomplete index.
- **Why it fails:** "Content stored" and "content fully processed" share one marker (the content hash / fingerprint). There is no per-item processed marker written at the end of a successful `classify_and_store`, and the intermediate phases are not transactional, so a partial item is indistinguishable from a finished one. The same non-atomicity means a crash between `DELETE FROM chunks` and re-insert in `store_doc_chunks` ([pipeline.rs:1257](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:1257)) leaves an item with no document chunks at all.
- **Status:** Confirmed by code trace. The happy-path folder test ([pipeline.rs:1494](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:1494) region, `folder_sync_skips_unchanged_files`) does not exercise cancel-mid-item.
- **Minimal fix:** Record processing completion separately — e.g. only persist the fingerprint/content-hash-as-processed (or a `processed_hash` column) in the final `finalize` step, and make `store_doc_chunks` delete+insert one transaction. A cheaper partial fix: on `job cancelled`/error, clear the item's fingerprint so the next sync re-extracts it.
- **Regression test:** Sync a folder, cancel during classification of a multi-window file (or inject a classifier failure after upsert), re-sync, and assert the item ends with the same entity/chunk counts as an uninterrupted sync.

### F-04 — High — FTS retrieval applies `LIMIT` before source/section filtering, so scoped searches starve

- **Where:** [retrieval.rs:496](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/retrieval.rs:496) `exec_fts_search` runs `... WHERE chunks_fts MATCH :q ORDER BY rank LIMIT :limit` and only afterwards filters by source/section in memory via `hits_from_ranks` → `load_hits_filtered` ([retrieval.rs:468](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/retrieval.rs:468)). The vector twin does the opposite: it appends source/section filters to the SQL **before** `AND k = ?` ([retrieval.rs:441](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/retrieval.rs:441)).
- **Scenario:** In a corpus where one large source dominates BM25, a project-scoped question (or `/qa/public`, or a TOC leaf search fenced to ten sections at [retrieval.rs:892](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/retrieval.rs:892)) asks FTS for the global top `top_k × 10` rows. If the scoped subset's best matches rank below that global cut-off, they are never fetched, the in-memory filter discards everything else, and keyword search returns empty — while the identical unscoped query, or the vector leg alone, finds them. Answers then degrade to vector-only or "no relevant knowledge" for exactly the scoped/share-safe surfaces.
- **Why it fails:** Candidate generation and scoping are in the wrong order for one of the two hybrid legs. `CANDIDATE_MULT = 10` ([retrieval.rs:328](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/retrieval.rs:328)) only widens the global pool; it cannot recover a scoped match ranked 500th globally. The TOC path is the most exposed because its section fence is applied exclusively in memory on the FTS side.
- **Status:** Confirmed by code trace (the asymmetry with `exec_vec_search` is visible side by side). Existing TOC tests seed single-source corpora, where the bug cannot fire.
- **Minimal fix:** Push `source_id`/`section_id` (and the leaf-kind clause's join columns) into the FTS SQL as the vector path does, so `LIMIT` applies to the scoped candidate set.
- **Regression test:** Two sources: a large one with many high-BM25 matches, a small project source with the only scoped match ranked low globally. Assert `keyword_search` with the project scope (and `toc_search` with a section fence) returns the scoped hit.

### F-05 — High — The manual document PII mark is visible in the UI but enforces nothing

- **Where:** The mark is stored and round-tripped ([items.rs:312](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/items.rs:312), exposed as `item_is_pii` at [entities.rs:56](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/entities.rs:56)), but every cloud-flow gate keys off the **source label only**: the answer/search gate at [answer.rs:750](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/answer.rs:750) (its own comment at [answer.rs:764](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/answer.rs:764) records that the item half is a follow-up), classification trust at [pipeline.rs:793](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:793), and the embed gate at [pipeline.rs:1460](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:1460). The toggle's UI copy is at [EntitiesTab.tsx:366](/Users/aleksandrtsirkunov/anchorcore/frontend/src/tabs/EntitiesTab.tsx:366).
- **Scenario:** A user opens a contract in the Entities tab, clicks "Mark PII", and reasonably believes the document is now protected. The source stays labelled `internal`. On the next reclassify, the document text is sent to the configured cloud classifier and embedder, and `POST /qa` happily includes its chunks in a cloud-composed answer — the mark changed nothing except a badge. (Direct reads such as `GET /items/:id` also return marked text ungated, which is defensible for a local owner but compounds the impression that the mark is a display flag, not a control.)
- **Why it fails:** The feature shipped as "advisory + visible" (R35.1) with enforcement deferred (R35.2), but nothing in the UI says "advisory". A privacy control that does not control anything is worse than none, because it changes user behaviour (they stop treating the document as exposed).
- **Status:** Confirmed; the label-only behaviour is pinned by a test ([answer.rs:1337](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/answer.rs:1337) `gate_answer_hits_filters_by_source_label_only`), so this is an intentional-but-undisclosed trade-off — flagged for its user-facing impact, per review rules.
- **Minimal fix:** Either enforce it (treat `item_is_pii = 1` like a `pii` source label in `gate_answer_hits`, the classify/embed gates, and the F-02 backfill exclusion) or label the toggle "Mark PII (display only — does not restrict providers yet)". Enforcement is one join away in each gate and is the right call before wider release.
- **Regression test:** Mark an ordinary-source item `is_pii`, then assert `search`/`ask` with an untrusted answer provider withholds its hits and a reclassify does not call the cloud classifier/embedder for it.

### F-06 — Medium — "Local provider" is a string prefix test, so lookalike URLs are trusted with sensitive content

- **Where:** [common.rs:29](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/common.rs:29) `provider_trusted` returns `true` for any base starting with `http://localhost` or `http://127.0.0.1`, with no host boundary. The same flawed check is duplicated at [classifier.rs:71](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/classifier.rs:71), [embedder.rs:57](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/embedder.rs:57), [answer.rs:1154](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/answer.rs:1154), [answer.rs:1178](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/answer.rs:1178), [settings.rs:451](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/settings.rs:451), [system.rs:14](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/system.rs:14) and [health.rs:54](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/health.rs:54). Notably, the `ANCHOR_TRUSTED_PROVIDERS` branch a few lines below *is* boundary-safe and even documents why ([common.rs:21](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/common.rs:21)).
- **Scenario:** `answer_base_url` is set — by a tricked operator, a copied config snippet, or a crafted settings payload — to `http://localhost@attacker.example/v1` (URL userinfo: the real host is `attacker.example`) or `http://localhost.attacker.example/v1`. Every trust gate reads it as "local", so sensitive/PII hits are composed by, and document windows are classified/embedded at, the attacker's endpoint, with the user's API key attached where configured.
- **Why it fails:** `starts_with` on a URL string is not a host check. `reqwest` parses the authority correctly and connects to the attacker host; only the gate is fooled. The blast radius is bounded by needing write access to settings (or social-engineering the operator), hence Medium rather than High — but the fix is trivial and the pattern is copy-pasted into eight places, so it will keep spreading.
- **Status:** Confirmed by code trace; `provider_trusted` tests ([common.rs:97](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/common.rs:97)) cover the allowlist boundary but never a localhost lookalike.
- **Minimal fix:** Parse the URL once (e.g. `url::Url`) and trust only hosts exactly equal to `localhost`, `127.0.0.1` or `::1`; replace all eight prefix checks with that single helper.
- **Regression test:** `provider_trusted("http://localhost@evil.example/v1") == false`, `provider_trusted("http://localhost.evil.example") == false`, `provider_trusted("http://127.0.0.1@evil.example") == false`, with the existing true cases unchanged.

### F-07 — Medium — A no-match question is answered from the newest documents, with citations

- **Where:** [retrieval.rs:945](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/retrieval.rs:945) `keyword_fallback` returns the most recently created leaf chunks (`ORDER BY c.created_at DESC`, [retrieval.rs:969](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/retrieval.rs:969)) with no relevance test. It is wired in at [answer.rs:696](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/answer.rs:696) whenever the embedder is unavailable and FTS finds nothing; `ask` then treats any non-empty hit list as evidence ([answer.rs:507](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/answer.rs:507)).
- **Scenario:** With Ollama down (keyword-only mode, the common first-run state), a user asks about something that is not in the corpus at all. Instead of "no relevant knowledge", they get a composed or context-only answer built from whatever was ingested last, complete with `[S1]`-style citations to documents that do not mention the question. This is the citation-accuracy failure mode the review was asked to hunt for: the citations are real chunks, but they do not support the claim.
- **Why it fails:** The fallback exists so a degraded engine still shows *something*, but it discards the one signal that matters — that nothing matched. `mode`/`retrieval` flags honestly report degradation of *mechanism*, yet the answer text still presents the unrelated context as the answer's basis.
- **Status:** Confirmed by code trace.
- **Minimal fix:** Drop `keyword_fallback` from the `ask` path (keep it, if wanted, behind an explicit "show recent" UI affordance), so a no-match query returns the existing "No relevant knowledge found yet" response. If product wants the behaviour, label the response `mode: "none"` with a "no match — showing latest documents" banner and no citations.
- **Regression test:** Keyword-only engine, seed documents, ask a nonsense question with zero token overlap; assert `mode == "none"` (or empty citations) instead of citations to the seeded documents.

### F-08 — Medium — Cancellation is advisory: the cancelled job keeps working and the queue overruns its bound

- **Where:** [jobs.rs:136](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/jobs.rs:136) `cancel` only flips the DB row and immediately promotes the next pending job ([jobs.rs:145](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/jobs.rs:145)). The running pipeline notices cancellation only between documents ([pipeline.rs:522](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:522), [pipeline.rs:574](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:574)) and between classification batches ([pipeline.rs:851](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:851)); an in-flight window batch (up to 4 concurrent LLM calls with a 60 s timeout each) and the whole finalize chain run to completion and commit their writes. There is no `AbortHandle`/token shared with the spawned task ([sources.rs:333](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/sources.rs:333)).
- **Scenario:** Two syncs are running; a third is queued. The user cancels sync #1 to free capacity. Sync #3 starts immediately, while #1 spends up to another minute calling the classifier and writing entities/chunks for its current document — three pipelines now contend for the two-slot bound, the provider rate limit, and the single SQLite writer. `finish_job` correctly refuses to overwrite the `cancelled` status ([pipeline.rs:472](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:472)), so the symptom is wasted paid provider calls and write contention, not corrupt job state — and it compounds F-03.
- **Why it fails:** Cancellation state lives only in the jobs table; nothing signals the actual task. `JobManager.running` is a bookkeeping map, not a set of task handles.
- **Status:** Confirmed by code trace.
- **Minimal fix:** Store a per-job `tokio::sync::watch`/cancellation token (or the task's `AbortHandle`) in `JobManager` at spawn, signal it in `cancel()`, and check it before each finalize phase — aborting the task outright is acceptable if F-03's processed-marker fix lands with it.
- **Regression test:** Start a sync against a slow mock classifier, cancel mid-document, and assert no further classifier requests arrive and no second pipeline exceeds the concurrency bound.

### F-09 — Medium — Deleting a source leaves its credentials behind, and a recycled id can inherit them

- **Where:** [sources.rs:237](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/sources.rs:237) `delete_handler` removes the row (FK cascade cleans items/chunks) but never touches the `SecretStore`; secrets are keyed `source:{id}:{field}` ([secrets.rs:120](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/secrets.rs:120)) in per-key files ([secrets.rs:52](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/secrets.rs:52)). `sources.id` is `INTEGER PRIMARY KEY` without `AUTOINCREMENT` ([01_initial.sql:2](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/migrations/01_initial.sql:2)), so SQLite may hand the deleted max id to the next created source. The resurrection path is [sources.rs:52](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/sources.rs:52) `mask_secrets` (reports `***set***` whenever a stored value exists for the id) and [pipeline.rs:23](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:23) `resolve_config`.
- **Scenario:** A user deletes a Jira source that held an API token, then creates a new source; it receives the same id. The config endpoint now shows the token field as `***set***` for a source that never had one, and if the user saves the form as-is, the old token is silently attached to — and used by — the new connector.
- **Why it fails:** The audit-trail comment in the handler ("delete means delete") is honoured for documents but not for the credential store, which has no cascade. Id reuse turns a hygiene leak into a wrong-credential bug.
- **Status:** Confirmed by code trace.
- **Minimal fix:** In `delete_handler`, delete `source:{id}:{field}` for every field in `SECRET_SOURCE_FIELDS` after the row delete. (Optionally also switch `sources` to `AUTOINCREMENT`, but the secret cleanup is the fix; id reuse alone is harmless once secrets are gone.)
- **Regression test:** Create a source with a token, delete it, create another source, assert `GET /sources/{new_id}/config` shows no `***set***` and the secret store has no `source:{new_id}:*` keys.

### F-10 — Low — Age decay is silently a no-op for real rows

- **Where:** [retrieval.rs:1149](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/retrieval.rs:1149) parses `chunks.created_at` with `DateTime::parse_from_rfc3339`, but every writer stores SQLite format (`CURRENT_TIMESTAMP` / `datetime('now')`, e.g. [pipeline.rs:1012](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:1012)) — `2026-10-13 12:00:00`, which is not RFC 3339. The parse fails, the map holds `None`, and `age_decay` returns `1.0` ([retrieval.rs:154](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/retrieval.rs:154)).
- **Scenario:** An operator sets `ANCHOR_RETRIEVAL_AGE_HALFLIFE_DAYS=30` expecting stale meeting notes to fade. Ranking never changes; year-old chunks compete at full score forever.
- **Why it fails:** Format mismatch between the SQLite timestamp convention and the single parse site; the failure is swallowed (`.ok()`), so nothing logs.
- **Status:** Confirmed by code trace (all insert sites use `datetime('now')`/`CURRENT_TIMESTAMP`; the only RFC-3339 producer in this path is the parser's expectation).
- **Minimal fix:** Parse with a SQLite-format fallback (`NaiveDateTime` `"%Y-%m-%d %H:%M:%S"` interpreted as UTC) before giving up.
- **Regression test:** Insert a chunk with `created_at = datetime('now', '-365 days')` via SQL, fuse it against a fresh identical chunk, assert the old one's score is decayed (≈ ×0.5 at a 365-day half-life).

### F-11 — Low — Two answer tests are not hermetic on a developer machine

- **Where:** [answer.rs:1420](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/answer.rs:1420) and [answer.rs:1449](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/answer.rs:1449) assume no answer API key exists; [settings.rs:139](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/settings.rs:139) resolves secret settings from the OS keychain, which on a configured dev machine holds a real key (temp-dir fallback path does not isolate the keyring; `SecretStore::new` only honours the fallback when `ANCHOR_SECRETS_NO_KEYRING=1`, [secrets.rs:20](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/secrets.rs:20)).
- **Scenario:** A developer runs plain `cargo test` on their workstation: 308 pass, these 2 fail with answers reading "[Answer model unreachable…]" instead of "No model key…". CI is green, so the failure reads as a phantom regression and erodes trust in the suite.
- **Why it fails:** Test isolation depends on an env var the tests themselves do not set.
- **Status:** **Reproduced** in this review (failed without the var, 310/310 green with it).
- **Minimal fix:** Have the two tests construct their `SettingsService` with the keyring disabled (or set/clear the relevant env under the existing test `ENV_LOCK` pattern used in `secrets.rs` tests).
- **Regression test:** The fix is the test change; guard it by running the suite once with a keychain entry present.

## 4. Hypotheses checked and not reported as defects

- **Graph expansion chunk identity:** [retrieval.rs:1103](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/retrieval.rs:1103) uses `cid.unwrap_or(eid)` when an entity has no chunk, which would alias an unrelated chunk id in citation lookups. In current code every stored entity gets a chunk ([pipeline.rs:1226](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:1226)), so the trigger needs legacy/imported data with a chunk-less entity; the multi-chunk entity case also collapses to one arbitrary chunk via the `by_id` map ([retrieval.rs:1096](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/retrieval.rs:1096)). Worth a defensive `continue` for `cid.is_none()`, but not counted as a confirmed finding.
- **Prompt injection via ingested documents:** Document text is placed in the classifier/distill user message without delimiting ([classifier.rs:174](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/classifier.rs:174)), and extracted `summary` text — not source bytes — becomes the entity chunk that retrieval later cites ([pipeline.rs:1227](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/pipeline.rs:1227)). A crafted document can therefore try to manufacture high-confidence "decisions". This is inherent to LLM extraction and partially mitigated (kind allowlist, confidence clamp, `window_text` retained for review at [classifier.rs:241](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/classifier.rs:241)), so it is recorded as a design risk to monitor, not a bug. The answer prompt itself ([answer.rs:1205](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/answer.rs:1205)) instructs context-only answers; there is no post-hoc check that emitted `[S#]` markers map to the returned citations, which is acceptable only while citations are presented as "sources consulted" rather than per-claim proof.
- **MCP input handling:** Tool arguments are read defensively (`as_str`/`as_i64` with defaults, `k` range-checked at [mcp.rs:233](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/mcp.rs:233)); malformed calls degrade to tool errors, not panics. `get_entity` is intentionally ungated (it is a local owner read), but note it makes the `gated_provider` refusal in `search`/`ask` a provider-protection measure only — an MCP client that can call `get_entity` with guessed sequential ids can still read entity windows. That is consistent with the local-first threat model; it should be stated in the MCP tool description so agent harnesses do not treat the refusal as a confidentiality boundary.
- **Backup import:** Zip-slip is rejected ([backup.rs:1719](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/backup.rs:1719)), entries are size/ratio-capped ([backup.rs:1693](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/backup.rs:1693)), hostile Argon2 parameters are refused ([backup.rs:152](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/backup.rs:152)), the bundle is decrypted before any write ([backup.rs:1965](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/backup.rs:1965)), and import is one transaction with a pre-replace safety backup ([backup.rs:1967](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/backup.rs:1967)). The one gap worth noting: the uploaded archive file itself is streamed to disk without a byte cap in `save_upload` ([backup.rs:2074](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/backup.rs:2074)) — an authenticated local user can fill the data volume; entry caps only apply after the upload completes. Low priority given the caller must already be trusted.
- **Folder path traversal:** The folder connector roots everything at the configured path, does not follow symlinks in the walk ([folder.rs:40](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/connectors/folder.rs:40)), and `GET /system/fs` lists directories only, never file bytes ([fsbrowse.rs:71](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/fsbrowse.rs:71)). Log download is allowlist-validated ([system.rs:339](/Users/aleksandrtsirkunov/anchorcore/rust/crates/anchorcore/src/system.rs:339)). No traversal finding survived tracing; the exposure question for these endpoints is F-01 (who can reach them), not the paths themselves.
